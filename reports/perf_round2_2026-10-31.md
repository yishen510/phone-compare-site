# 性能瓶颈分析与针对性优化（第二轮）

## 一、优化目标与衡量指标

**目标**：缩短「用户看到第一屏内容」的时间，并降低浏览器布局成本；功能与视觉保持不变。

**指标**（移动端 390×844 + CPU 4× 降速，Edge headless + CDP）：

| 指标 | 含义 | 采集方式 |
| --- | --- | --- |
| 首张卡片可见 | 用户真正「看到内容」的时刻 | 轮询 `#phoneGrid .phone-card` 出现 |
| 全部画完 | 485 张卡片全部分批绘制完成 | `grid.dataset.painting==='0'` |
| LayoutDuration | 累计布局耗时 | `Performance.getMetrics` |
| RecalcStyleDuration | 累计样式重算耗时 | 同上 |
| ScriptDuration | 累计 JS 执行耗时 | 同上 |

> 上一轮的经验：单次 `painting=0` 波动可达 20–40%，因此本轮新增 Layout/RecalcStyle/Script 三项浏览器侧指标，交叉判断瓶颈到底在 JS 还是布局。

## 二、瓶颈分析（实测，非推测）

优化前基线：

```
首屏首张卡片可见   3648 ms
首屏到卡片画完     7788 ms
累计 Layout        4398 ms   ← 占首屏 56%
累计 RecalcStyle   1226 ms
累计 Script         402 ms   ← 仅占 5%
```

**结论**：JS 执行只占 5%，**瓶颈在浏览器布局（Layout）**。原因是 485 张卡片 × 约 20 个元素 ≈ 1 万 DOM 节点，加上 `backdrop-filter:blur(22px)` 的合成成本。

同时确认：卡片已有 `content-visibility:auto`（618 行），屏幕外内容本应被跳过；但首屏同步插入 **48 张卡片（约 8–10 屏）**，远超实际可见范围，导致首帧就要布局大量本不需要立即布局的卡片。

## 三、实施的优化

### 1）首屏同步绘制 48 → 12 张（核心）

- **范围**：`index.html` 常量 `PAINT_FIRST`（1 处），不改分批逻辑、不改 `PAINT_STEP`/`PAINT_BUDGET`。
- **原理**：首帧只同步插入约 3 屏卡片（12 张），其余 473 张继续由原来的 rAF 分批（每帧 96 张、8ms 预算）补齐。首帧要构建 + 布局的 DOM 减少约 75%。
- **约束**：最终仍绘制全部 485 张，数据流与交互不变；低端设备快速滚动时理论上可能短暂看到未绘制区域，但分批在约 5 帧（<100ms）内补齐。
- **实测**（两次）：

| 指标 | 优化前 | 优化后 ① | 优化后 ② |
| --- | --- | --- | --- |
| 首张卡片可见 | 3648 ms | **3314 ms** | **3356 ms** |
| 全部画完 | 7788 ms | 7077 ms | 6678 ms |
| Layout | 4398 ms | 4037 ms | 3983 ms |
| RecalcStyle | 1226 ms | 1227 ms | 976 ms |
| Script | 402 ms | 378 ms | 314 ms |

首张卡片稳定 **-8~9%**，Layout 稳定 **-8~9%**。

### 2）`card()` 重复 Set 查询 3 → 1

- **范围**：`card()` 内 `state.favs.has(p.id)` 出现 3 次，提取为 `const fav=...`。
- **收益**：每轮渲染少 970 次 `Set.has`（485 × 2）。量级很小，但确定为正，且不改变任何输出。
- **验证**：`check_new_features`（收藏）、`check_detail_features`（收藏按钮文案）通过。

## 四、尝试后回退（负收益，已写注释防重踩）

| 尝试 | 预期 | 实测 | 处理 |
| --- | --- | --- | --- |
| `esc` 改「先 test 再 replace」 | 少建映射对象 | **慢 10.8%** | 回退，注释写明原因 |
| `money` 加 `Map` 缓存 | 省 Intl 开销 | **慢 6.5%** | 回退，注释写明原因 |
| `contain-intrinsic-size` 由 `auto 420px` 改固定 `420px` | 省一次测量 | 单次更差（首屏 9706ms / Layout 4956ms） | 回退 |

原因：`esc` 的回调只在**命中特殊字符时**才创建对象，无匹配时 `replace` 已足够快；`toLocaleString` 在 V8 中已缓存 Intl 格式器，`Map` 查找反而更慢。

## 五、明确不做的优化及原因

| 方案 | 预期收益 | 不做的原因 |
| --- | --- | --- |
| 虚拟滚动（只渲染可视行） | 最大，可把首屏降到 1–2s | 需接管滚动与高度估算，改动大、搜索/收藏状态易出错，风险高于本轮目标 |
| 移除卡片 `backdrop-filter` | 显著降低合成成本 | 视觉风格改变，不符合「保持功能与外观不变」 |
| 拆分外部 JSON | 首屏解析大幅下降 | 破坏单文件站点结构（离线直开退化），需独立议题 |
| 表格分批 | 无 | 上一轮已实测劣化（排序 3.5s→13.4s）并回退 |
