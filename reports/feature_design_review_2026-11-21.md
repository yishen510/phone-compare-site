# 机选 · 功能设计与优化方案评审

- 评审对象：`_deploy_phone/index.html`（评审时 3413 行 / 1.42 MB，含内联数据 488 条；P0 落地后 971 KB）
- 评审日期：2026-11-21（P0 实施 2026-11-23，见第 7 节）
- 评审方式：代码通读 + jsdom 运行时探针 + 数据字段引用扫描（所有结论都可复现，附录给命令）
- 约束：不改变产品原目标——**帮中国大陆用户选购手机时做参数对比与决策**

---

## 0. 一句话结论

主链路是健康的：**筛选 → 对比 → 决定** 这条路径跑得通，数据治理的严谨度在同类站点里罕见。

但外围挂了三层与主线脱节的重量：**审计治理层、实时报价层、推荐打分层**。

- 审计台账（`auditNotes` 等 10 个字段）占首屏数据字节的 **42%**，而代码里**一次都没读过**；
- 实时报价层覆盖 **1 / 488** 台，却带着约 200 行前端逻辑和一整套后端服务；
- 推荐打分层按项目自己的准入政策应有 **0 台**可用，实际靠绕过门槛的启发式在跑。

三层合计约 300 行 JS。同时，上一轮"详情按需加载"的重构留下两个**未被测试覆盖的回归**，其中一个让全库规格搜索彻底失效。

所以优化重点不是加功能，是**把治理数据留在治理层，把首屏还给决策**。

## 1. 目标用户与核心场景

### 1.1 三类真实用户（按使用路径分，不按人口属性分）

| 类型 | 占比估计 | 进来时知道什么 | 离开时想得到什么 | 当前满足度 |
|---|---|---|---|---|
| **A 预算换机者** | ~60% | 预算 3000–4000，用了几年的旧机 | 这个价位有哪几台值得看、差别在哪 | 中（筛选用得了，但"值得"没人回答） |
| **B 决赛圈核对者** | ~25% | 已看中 2–3 台 | 屏幕/电池/重量/影像到底差多少 | 较好（对比表是强项） |
| **C 数据引用者** | ~15% | 无，来找可溯源的参数 | 数值 + 来源链接 | 好（详情证据链完整） |

判断依据：现有功能重心（九字段溯源、`AUDIT_POLICY`、来源标注）全部服务 C；对比表的质量服务 B；A 只有筛选器和一张卡片。

### 1.2 四个核心场景

1. **预算内海选**：设价格带 → 看列表 → 排序（首发价/重量/屏幕）→ 挑 2–4 台
2. **决赛圈对比**：并排看差异 → 只看差异 → 导出/截图 → 做决定
3. **单台查证**：打开详情 → 看九字段 + 规格分组 → 追来源
4. **回访**：收藏 / 最近浏览 / 分享带参数的链接

### 1.3 一个必须说清的判断

**场景 2 是产品存在的唯一理由**，其余三个都是它的支撑。

但当前投入是倒过来的：场景 3 的工程量最大（九字段审计 + 规格分组 + 来源），场景 2 只做到"把不同值标红"。用户真正的痛点——"这四台里我该买哪台"——目前没有任何一处功能在回答。这不是要加"AI 推荐"，而是对比结果缺少一句可读的结论。

## 2. 主要问题（按严重度）

### P0-1｜全库规格搜索失效（功能性回归，已实测）

**现象**：搜只在参数里出现的词，返回 0 条。

```
搜「IP68」  → 0 条   规格库实际 214 台
搜「LTPO」  → 0 条   规格库实际  64 台
搜「超声波」→ 0 条   规格库实际 110 台
搜「潜望」  → 95 条  ← 假象：命中的是 card 的 camera 字段，不是规格
```

**根因**（`index.html:2301-2308` + `1842` + `3322`）：

```js
function specHay(p){
  if(SPEC_HAY.has(k)) return SPEC_HAY.get(k);
  specList(p).forEach(...);   // specs 未加载时 → t = ''
  SPEC_HAY.set(k,t);          // ← 把空串永久写进缓存
}
```

`warmSearchIndex()` 在首屏 idle 时对全部 488 台跑一遍 `specHay`，此时 `specs` 还在 `data/detail/` 里没拉，于是 **488 条缓存全部被写成空串**。之后 `matchQuery` 永远读到空串。

叠加第二个 bug：`tightSpec()` 另有 `TIGHT_SPEC` 缓存，而 `loadDetail` 成功后只清了 `SPEC_LIST_CACHE` 和 `SPEC_HAY`（`2349`），**`TIGHT_SPEC` 永不失效**，所以"去空格再匹配一次"这条路也永久失效。

**为什么测试没抓到**：`_jst/check_search.js` 只测了 `小米15 / 荣耀Magic8 / X300 / 骁龙`——这些都是 card 字段里就有的词，规格索引挂了也照样通过。测试覆盖的是"搜索框能用"，不是"规格能被搜到"。

### P0-2｜数据说明面板自曝"有完整参数 0"（展示性回归，已实测）

点页脚「数据说明」，面板显示：

> 机型 488 · 品牌 20 · **有完整参数 0 · 参数条目 0 · 平均字段/台 0** · 最近采集 2026-11-21

**根因**：`dataSummary()`（`2389`）直接读 `p.specs`，但 `specs` 已被拆到按需文件，首屏从未加载。同一个拆分动作，把"数据说明"变成了"数据缺失说明"。

这条比 P0-1 更伤：它是**主动向用户展示的自我否定**，而且出现在最需要建立信任的位置。

### P0-3｜首屏四成数据，代码一次都没读过

对内联数据做全字段引用扫描（在 JS 里搜字段名），10 个字段**零引用**：

| 字段 | 字符数 | JS 引用次数 | 实际用途 |
|---|---:|---:|---|
| `auditNotes` | 95,299 | **0** | 审计台账，属治理层 |
| `quoteTargetStorageReason` | 23,614 | **0** | 报价口径说明，属治理层 |
| `announcementSource` | 20,842 | **0** | 发布稿来源 |
| `storageOptions` | 15,230 | **0** | 容量组合（`hwOf` 另从 `storage` 文本解析） |
| `priceAuditStatus` | 14,095 | **0** | 价格审计状态 |
| `scoreMethod` / `sourceName` / `priceSourceName` / `quoteTargetStorage` / `parameterAuditStatus` | 40,825 | **0** | 同上 |
| **合计** | **209,905** | — | 占数据字符 24.4%、数据字节约 42% |

实测剔除这 10 个字段后（不含后来新增的特征位）：

```
整页   1,420 KB → 932 KB   (-34%)
gzip     164 KB → 131 KB   (-20%)
```

**这不是"该不该瘦身"的问题，是"审计台账被当成首屏数据下发"的架构错位**。这些字段的唯一读者是审计脚本和人，它们应该留在 `data/phones.json` 里。

### P1-1｜准入门槛有政策，但产品层没执行（两套互相矛盾的答案）

`modelPassed`（`1573`）要求 `auditStatus === 'verified'` 且双资格 + 九字段全证据。全库实测分布：

```
needs_parameter_price_audit  413
partial_verified              35
（null）                      35
pending_review                 5
verified                       0   ← 一次都没出现
```

也就是说**按政策，488 台没有一台有资格被推荐**。但 `rankingCandidates` / `recommendationCandidates`（`1578-1579`）**从未被任何地方调用**——只有定义，没有调用点。真正在跑的是 `recommendForNeeds`（`2265`），它对年份/预算池直接 `scoreFor` 打分取前 8，完全绕过审计门槛，只在文案里加一句"参数匹配参考，非正式推荐"。

结果：`AUDIT_POLICY.md` 写的"未通过准入不得推荐"在产品里**没有生效**，只靠一句免责文案软化。政策与实现各说各话，这是最容易被外部质疑的点。

### P1-2｜实时报价层空转

```
livePriceStatus:  not_connected 487 台 / official_store_snapshot 1 台
```

99.8% 的机型没有实时价，但代码里有：报价卡、API 状态灯、刷新与进度条（`2590-2795`，约 200 行）、`price_server.py`（32 KB 后端）、隧道与部署配置。

这是一整套**第二个产品**（实时报价服务），数据覆盖率 0.2%，且没有获授权的上游。它给用户的是"待核实"三个字，给维护者的是持续成本。

### P1-3｜筛选会静默吃掉未知值机型

`matchFilters`（`1766`）：

```js
if(state.priceMin!=null&&(!Number.isFinite(price)||price<state.priceMin))return false;
```

库里 **130 台（26.6%）`priceCN` 为空**。用户一旦设价格带，这 130 台全部消失，而空态文案只说"试着移除一项筛选 / 扩大年份范围"，不会告诉用户"另有 130 台因价格待核被排除"。硬件筛选同理（`hwOf` 从展示文本里抠数字，抠不到就排除）。

**未知值被当成不满足条件**，是筛选类产品最容易失去信任的地方。

### P1-4｜详情加载失败即永久放弃

`loadDetail`（`2331`）：

```js
.catch(()=>null)
.then(d=>{ DETAIL_LOADED.add(id); ... })   // 失败也标记已加载
```

请求失败（弱网、404、SW 缓存损坏）后，该机型被标记为"已加载"，**本次会话内不再重试**。用户只看到"参数待补充"，没有任何提示、没有重试入口。`cache:'force-cache'` 又让陈旧响应难以刷新。

### P2-1｜`state` 没有单一真相

初始化器（`1592`）声明 16 个字段，实际运行期用到 27 个：

```
未被声明、运行中挂上去的：hw / pageMode / recent / onlyIds / recommendIds /
selected / lastArr / visibleCount / detailList / detailPos / compareQuery /
compareSort / pendingCompare / pendingModel
```

另有 2 个**死字段**：`limit`、`sig`——全文件 0 引用，是分页重构后的残留。

后果：任何新代码都不知道 state 的完整形状，只能靠 `state.hw||{}` 这类防御写法兜。

### P2-2｜`render()` 一个函数干 13 件事

`render`（`2092`）在一次调用里完成：品牌筛选器重绘、过滤、统计数字、分页重置、网格绘制、分页条、批量栏、空态文案、网格显隐、对比坞、活动筛选条、最近浏览、URL 同步、优先级 chips。

任何一处状态变化（点个收藏、切个视图）都会重跑全部 13 件。这也是为什么需要 `gridSignature` 这种缓存键来兜底——**因为没法只重绘变化的部分**。

### P2-3｜缓存键过弱，中间项变化不重绘

`gridSignature`（`2040`）用 `长度 + 首项 id + 末项 id + 排序 + 收藏串` 做键。若筛选变化后结果数量、首项、末项都不变（只是中间换了几台），签名不变 → **不重绘 → 列表停在旧数据**。分页重置用的 `fkey`（`2100`）是同一套弱键，同一个问题。

概率低但一旦发生就是"点了没反应"，比慢更伤。

### P2-4｜弹层没有焦点管理

`openModal`（`2130`）只做 `innerHTML` + `hidden=false`；`closeModal`（`2131`）只做隐藏。三个弹层都标了 `role="dialog"` + `aria-modal="true"`，但：

- 打开后焦点不进入弹层，键盘用户仍在背景页
- 没有 focus trap，Tab 会走到遮罩后面
- 关闭后焦点不回到触发按钮

`aria-modal="true"` 在没做 focus trap 的情况下是**错误声明**，会让读屏器跳过背景内容，实际焦点却在背景——比不写更糟。

### P2-5｜文档漂移

`DATA_STATUS.md` 仍写 155 条，实际 488 条（差 3 倍）。同类问题会让人不敢信任何一份说明文档。

## 3. 六个维度的诊断

### 3.1 功能边界（最需要收紧）

| 功能 | 是否属原目标 | 真实数据支撑 | 判断 |
|---|---|---|---|
| 筛选 / 排序 / 对比 / 详情 | 是，核心 | 488 台 | **保留，加大投入** |
| 收藏 / 最近 / 预设 / 分享链接 | 是，支撑回访 | 本地状态充足 | 保留 |
| PWA 离线 | 是，弱网场景 | 已实现 | 保留 |
| 九字段审计 | 是，但属**治理** | 488 台 | 保留，**移出首屏** |
| 实时报价 | 弱相关 | 1/488 | **收缩为可选入口** |
| 自动推荐 | 是，但需准入 | 0 台通过准入 | **要么真执行政策，要么明确降级** |

结论：边界问题是**把治理层的东西（审计台账、报价口径、来源说明）当成产品层下发**，同时又让产品层的准入政策空转。

### 3.2 模块职责

现状是「一个 IIFE + 130 个函数声明 + 47 个事件监听」，边界靠 `data-*` 属性约定维持。`document.addEventListener('click')`（`2796-2801`）是一行内 4 段以上 `if` 链的巨型委托，任何新交互都往这里加一段。

不是必须拆文件（单文件部署确实简单），但**至少要在文件内划出可识别的段**：数据层 / 状态层 / 选择器层 / 渲染层 / 交互层 / 持久化层。现在连注释分节都是断续的。

### 3.3 关键流程

以"设价格 3000–4000"为例，实际链路：

```
input → render() ×13 件事
      → filtered()（filter + sort，488 条全量）
      → wantsPaged → 重置 visibleCount
      → gridSignature 比对 → 可能不重绘（弱键）
      → updatePager → syncBatchBar → 空态判断 → updateCompare
      → renderActiveFilters → renderRecent → syncUrlState（history.replaceState）
      → syncPriorityChips
```

问题：**一次输入跑 13 件事，其中 9 件与"价格变了"无关**。年份/预算输入框直连 `render` 且**无防抖**（`2800`），搜索框反而有 160ms 防抖（`3172-3177`）——两者不一致。

`syncUrlState` 用 `history.replaceState` 且不节流，滚动/输入频繁时会连续调用。

### 3.4 异常处理

做得好的地方（值得作为标准推广）：

- `importFavsFile`（`2996`）：1MB 上限、try/catch、逐条校验并回报"新增 N / 忽略 M"
- 空态文案：能区分"没有收藏"、"筛选命中 0"、"暂无数据"，并给出可点的移除按钮
- `loadDetail` 有 400ms 延迟 toast（"正在载入规格…"）
- 对比年份填反有专门的纠正按钮

缺口：

- 详情加载失败静默、不重试、不提示（P1-4）
- 搜索/筛选无结果时不区分"确实没有"与"有但被未知值排除"（P1-3）
- 全局没有 `window.onerror` / `unhandledrejection` 兜底，一次脚本异常就整页卡死无提示
- `try{}catch(e){}` 有多处空 catch（如 `syncUrlState`），出错即静默

### 3.5 扩展性

| 扩展方向 | 当前阻力 |
|---|---|
| 加一个筛选维度 | 要同时改 `state`、`matchFilters`、`activeFilterChips`、`clearActiveFilter`、`reset`、`syncUrlState`、`restoreUrlState`、UI 六处 |
| 加一个字段 | 要改数据、卡片、表格列、对比行、详情分组、CSV 导出、`REQUIRED_FIELDS` |
| 加一种视图 | 要改 `paintGrid`、`gridSignature`、`wantsPaged`、`updatePager` |
| 换数据源 | 内联数据 + 按需文件 + `data/phones.json` 三份需同步，且**必须按固定顺序跑两个脚本**，顺序错了就静默丢字段 |

最后一条是真风险：新增机型时若忘了先跑 `sync_html_data.py` 再跑 `split_detail_data.py`，记录会进目录但详情为空，且**不报错**。

### 3.6 用户体验

优点：密度切换、键盘快捷键（`t/f/c/g/?`）、深链分享、空态可操作、移动端筛选折叠、滚动性能做过实测优化（`paintGrid` 分批 + 首帧同步）。

问题集中在四处：

1. **对比结论缺失**——并排标红差异之后没有一句"所以选哪台"
2. **未知值语义缺失**——26.6% 无机型价格，筛选一开就消失且不解释
3. **首屏重量**——1.42MB / gzip 164KB，4G 下仅传输就约 0.7–1.3 秒，之后还要主线程 `JSON.parse` 解析 86 万字符
4. **弹层键盘不可用**——焦点不进入、不能 Tab 循环、关闭不回位

## 4. 改进建议（按优先级）

> 每条给"改什么 / 在哪改 / 预期效果 / 怎么验收"。P0 当天可完成。

### P0｜先止血（1 天）

#### P0-A 修规格搜索缓存毒化

- **改**：
  1. `specHay` 里 specs 未加载时**返回 `''` 但不写缓存**（`2302-2308`）
  2. `loadDetail` 成功后追加 `TIGHT_SPEC.delete(id)`（`2349`）
  3. 补一条回归测试：打开过详情的机型，其规格专有词必须能搜到
- **预期**：不会再"永久毒化"；已加载过详情的机型立即能被规格词搜到
- **验收**：`node _jst/probe_regressions.js` 中 IP68 由 0 → >0（需配合 P0-B 才能覆盖全库）
- **注意**：只做这一步，全库规格搜索仍是残的——因为大部分机型从未被打开。**P0-B 才是根治**

#### P0-B 用"特征位"兑现参数搜索（原方案已修正）

> ⚠️ 本节初稿给的是"构建期生成轻量规格索引，预计 40–60KB"。**实测不成立**：
> 全库 488 台的规格全文约 100 万字，最省的编码（分词去重 + base36 倒排）gzip 仍有
> 134–181 KB，比整页还大；截断取值到 30 字虽能压到 134KB，但"潜望"召回从 92 台掉到 52 台。
> 也就是说：**规格全文搜索没法在首屏缓存里免费获得**。故改为特征位方案。

- **改**：在 `scripts/split_detail_data.py` 里定义 `FEATURE_TERMS`（25 条），构建期扫描每台规格，命中则写 `ft:["ip68","periscope",…]`；页面侧用 `FEATURES` 映射（id → 可搜文案）参与 `matchQuery`。新增特征只需在 `FEATURE_TERMS` 加一条并重跑脚本
- **预期**：IP68 / LTPO / 超声波 / 潜望 / 无线充 / 卫星 / 红外 等常见参数词可搜；首屏只增加约 8–12 KB（实测 +27 KB 原始 / 约 +7 KB gzip）
- **验收**：`IP68/LTPO/超声波` 命中数与 `data/detail` 里实际含该词的机型数一致（实测 214/64/110，全部吻合）
- **已知边界**：不是全文搜索——搜 `f/1.8`、`LPDDR5X 8533` 这类具体数值仍搜不到。若将来真要全文，只能做成"用户显式点击后才拉 134KB 索引"的按需加载，不该进首屏

#### P0-C 修数据说明面板

过程中发现并顺手处理的四件事：

1. **详情文件与主库漂移**：重跑拆分时 485 个详情文件的 `fieldAudit` 比主库少一个 `note` 字段。逐条比对确认「只新增 `note`，已有键的值 0 处变化」，属安全同步，予以保留（详情页审计底稿与主库自此一致）。
2. **`sw.js` 版本号**：代码与详情都变了，`VERSION` 由 `v1` 升到 `v2`，避免老用户吃到旧 shell。
3. **结果要有解释**：搜 `IP68` 出 214 台，但卡片上不会出现 "IP68" 字样。结果标签改为显示「含「IP68」」（只在结果并非由卡片可见字段命中时才加），否则用户会以为结果乱来。
4. **ProMotion 别名**：初版特征位只认 `ltpo`，漏了 8 台 iPhone Pro（规格页写的是 ProMotion）。已把 `promotion` 并入 `ltpo` 别名——ProMotion 本身就是 LTPO 面板。
