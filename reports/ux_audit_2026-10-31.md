# 用户体验审查清单（2026-10-31）

审查对象：`index.html`（单文件站点，442 条机型，内嵌数据约 2.5 MB / 文件 3.66 MB）
约束：保持现有功能与结构不变，只做低成本高收益优化，不引入大规模重构。
**本清单只做诊断与方案，尚未改动任何代码。**

---

## 一、审查方法与实测基线

| 手段 | 说明 |
|---|---|
| 真实浏览器基准 | Edge headless + CDP，移动端模拟 390×844、**CPU 4× 降速**，桌面 1440×900 对照（`_jst/ux_bench.js`） |
| 代码核查 | 键盘/焦点、aria、媒体查询、溢出与滚动、空状态与提示、固定定位元素 |
| 功能探针 | 收藏/对比/最近浏览/URL 状态等 11 项已有功能回归（`_jst/probe_features.js`，11 PASS） |

### 实测数据（关键痛点来源）

| 场景 | 桌面 | 移动端模拟（CPU 4×） |
|---|---|---|
| 首屏到卡片画完 | 1225 ms | **7087 ms** |
| 切到表格视图 | 1222 ms | **2636 ms** |
| 表格点击排序 | 304 ms | **3459 ms** |

### 已经做得不错、无需改动的部分

- 表格容器 `overflow:auto` + `min-width`（可横向滚动）、13 处媒体查询

## 二、改进清单（按影响程度排序）

### P0 — 影响面大且成本低，建议优先

#### 1. 表格视图在移动端卡顿（渲染 2.6 s / 排序 3.5 s）
- **现状**：表格视图一次性插入 442 行 × 7 列。卡片视图有分批绘制（`paintGrid`），**表格没有**，是唯一没走分批的重路径。排序虽有 `reorderTableRows` 行复用，但窄视口下 442 行重新布局依然要 3.4 s。
- **目标**：让移动端进入/操作表格不再明显卡顿。
- **预期收益**：移动端表格交互从秒级降到可感知的「即时」范围；避免用户误以为页面卡死。
- **实现要点**：把表格行也按 `paintGrid` 的思路分批插入（首屏 60 行 + 空闲补余下），插入期间保持表头不动；排序沿用现有 `reorderTableRows`，仅在「行数/对比状态变化」时才回退到重建。
- **改动范围**：`renderTable()` 及其调用点约 20–40 行，不动数据结构与功能。
- **风险**：低。分批期间若用户立刻排序，需保证排序走全量数组、只重排已插入行（或先补齐全量再排）。

#### 2. 首屏没有加载反馈（移动端 7.1 s）
- **现状**：3.66 MB 单文件解析 + 442 张卡片构建期间，页面没有任何加载指示（现有 7 处 `loading` 全是「渠道报价查询」的状态，与首屏无关）。用户在移动端可能看到较长时间的空/半空页面。
- **目标**：把不可缩短的等待变成可感知的进度。
- **预期收益**：感知性能显著提升，降低「是不是坏了」的跳出判断。真实耗时不变但主观体验改善明显。
- **实现要点**：在 `#phoneGrid` 初始位置放 8–12 个骨架卡片（纯 CSS，可复用现有卡片骨架类名），数据就绪/首批卡片插入后移除；骨架需带 `aria-hidden="true"`，避免读屏误播报。
- **改动范围**：HTML 加一段骨架容器 + CSS 一组骨架样式 + 首次 `render()` 后移除，约 30–50 行，不改数据流。
- **风险**：低。注意骨架只在首屏出现一次，后续筛选不再出现。

#### 3. 屏幕阅读器过度播报（`#phoneGrid` 上的 `aria-live="polite"`）
- **现状**：承载 442 张卡片的容器标了 `aria-live="polite"`，每次筛选/搜索都会让读屏软件尝试播报整块区域，实际效果是长时间刷屏，几乎无法使用。
- **目标**：让播报只传递「结果数量变化」这一条有效信息。
- **预期收益**：读屏用户从「不可用」变为「可用」，且改动极小。
- **实现要点**：`#phoneGrid` 去掉 `aria-live`（或设为 `off`）；给 `#resultCount` 加 `aria-live="polite"` + `aria-atomic="true"`，文案统一为「共 N 款机型」。
- **改动范围**：HTML 两处属性 + 结果计数文案，约 3–5 行。
- **风险**：低。这是无障碍标准做法。

#### 4. 固定对比栏遮挡页面底部内容
- **现状**：`.compare-dock` 为 `position:fixed;bottom:22px`，显示时页面**没有预留底部空间**，在移动端会盖住最后几张卡片与页脚。
- **目标**：出现对比栏时内容不被遮挡。
- **预期收益**：避免「最后一台机型点不到」的直接可用性问题。
- **实现要点**：对比栏显示时给 `body` 加一个类（如 `has-dock`），配 `padding-bottom: 96px`（移动端 120px）；隐藏时移除。
- **改动范围**：CSS 一条规则 + 显示/隐藏处各一行加删类名，约 5 行。
- **风险**：低。注意与「回到顶部」按钮的间距。

### P1 — 明确改善体验，成本仍可控

#### 5. 空状态缺少量化反馈与定向清除
- **现状**：文案为「没有找到符合条件的机型 / 试着移除一项筛选，或扩大年份范围」，有重置按钮，但没告诉用户「共 442 款，当前 0 款」，也没指出是哪一项筛选导致为 0。
- **目标**：让「为什么为空」和「怎么恢复」一目了然。
- **预期收益**：减少空结果时的迷茫与误判为「数据不全」。
- **实现要点**：空状态文案改为「共 {总数} 款，当前筛选命中 0 款」；把当前生效的筛选列成可点击的「移除」按钮（复用现有 `activeFilters` 的移除逻辑）。
- **改动范围**：空状态渲染函数，约 15–25 行。
- **风险**：低。

#### 6. 表格横向滚动没有提示，iOS 无惯性
- **现状**：`.table-wrap{overflow:auto}` 可横滑，但没有视觉提示；也未设置 `-webkit-overflow-scrolling:touch`。
- **目标**：让用户知道表格可以左右滑动。
- **预期收益**：移动端用户不再漏看右侧的「价格 / 充电 / 重量」列。
- **实现要点**：表格容器加右侧渐隐遮罩（CSS `mask-image` 或伪元素），滚动到尽头时隐藏；补 `-webkit-overflow-scrolling:touch`；可在表头区补一行小字提示「← 左右滑动查看全部列 →」（窄屏才显示）。
- **改动范围**：CSS 约 15 行 + 容器一处属性。
- **风险**：低。遮罩需同时适配深/浅两套主题。

#### 7. toast 无类型区分，关键操作不可撤销
- **现状**：`toast(msg)` 只有一种样式，2.3 s 后消失；移除收藏/对比项后无撤销入口，误触只能手动找回。
- **目标**：区分提示性质，并给破坏性操作一次撤销机会。
- **预期收益**：减少误操作损失，提示更易理解。
- **实现要点**：`toast(msg, type)` 增加 `ok/warn/error` 三态（仅改颜色与图标，不动布局）；针对「移除收藏」「清空对比」把最近一次操作存进一个变量，toast 内附一个「撤销」按钮（只保留最近一次，不做完整撤销栈）。
- **改动范围**：`toast()` 与 2–3 个调用点，约 25–40 行。
- **风险**：中低。撤销按钮需要键盘可达，并注意 2.3 s 自动消失与撤销的冲突（撤销出现时延长到 6 s）。

#### 8. 结果数变化对读屏用户无播报
- **现状**：`#resultCount` 是 `<strong>`，无 `aria-live`；与第 3 项是配套改动。
- **目标**：筛选后读屏用户能听到「共 N 款」。
- **改动范围**：同第 3 项，合并实施。
- **风险**：低。

## 三、取舍说明（为什么不做这些）

| 方案 | 收益 | 为什么不列入本次 |
|---|---|---|
| **把内嵌数据拆成外部 JSON / 分片加载** | 收益最大：首屏少解析 2.5 MB，移动端首屏可能从 7 s 降到 2–3 s | 会把「单文件站点」改成「多文件」，**违反本次「结构不变」约束**；且离线/直开场景会退化。建议作为后续独立议题评估。 |
| **表格虚拟滚动（只渲染可视行）** | 比「分批插入」更彻底，千行也稳定 | 需要接管滚动与行高，改动明显大于分批插入；现状 442 行用分批插入已足够，性价比更高。 |
| **完整撤销栈（多步撤销）** | 体验最好 | 需要维护操作历史与状态快照，中等成本；本次先用「最近一次操作的撤销」覆盖最高频的误触场景。 |
| **卡片骨架屏改成占位图/插画** | 视觉更好 | 与现有极简风格不一致，且会增加资源请求，收益不成比例。 |
| **搜索再加拼音/模糊匹配** | 覆盖面更广 | 现有搜索 144 ms 且刚修完空格归一化，再加模糊匹配容易引入误召回，收益不确定。 |

## 四、建议实施顺序

1. **第一批（约半天）**：第 3、4 项（读屏播报、对比栏遮挡）—— 几乎零风险，立刻见效。
2. **第二批**：第 2 项（首屏骨架屏）—— 改感知性能，不动数据流。
3. **第三批**：第 1 项（表格分批插入）—— 移动端最大的卡顿源，需配合回归测试。
4. **第四批**：第 5、6、7、8 项 —— 提示与反馈层打磨。
5. **P2 项**视时间挑选。

每批完成后建议跑：通用 25 项、功能探针 11 项、渲染扫描、`_jst/ux_bench.js` 复测移动端三项指标。
