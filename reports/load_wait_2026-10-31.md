# 等待时间优化：瓶颈定位、改进与验证

日期：2026-10-31
需求：*识别当前流程中的主要等待环节与性能瓶颈，明确可优化的加载/响应/交互节点，给出改进方向与优先级，并说明如何验证等待时间得到改善。*

---

## 一、怎么量的（先有尺子，再谈优化）

前面的性能工作都在 `file://` 上做，**没有网络耗时**，测不出"等下载"。这次补了一套带真实传输条件的测量：

| 工具 | 作用 |
|---|---|
| `_jst/serve_gzip.py` | 本地复现 GitHub Pages 的传输条件：gzip（线上 645KB ↔ 本地 621KB）+ ETag/304 + `max-age=600` |
| `_jst/load_bench.js` | 真实 Edge + CDP：网络限速 + CPU 降速，采 FCP/LCP/首卡/load/传输量/主线程归因，并测**回访**（同浏览器第二次打开） |
| `_jst/shot_timeline.js` | 按时间点截图，证明用户看到的是白屏还是内容 |

四个配置：网络 `fast` / `4g`（4Mbps、100ms RTT），CPU `1×` / `4×`（4× 约等于中端手机），视口 390×844。

## 二、主要等待环节（实测）

### 2.1 四种场景下的等待

| 场景 | 文档下载 | 首次内容 FCP | **看到列表** | load 事件 |
|---|---:|---:|---:|---:|
| 光纤 + 桌面 | 101 ms | 312 ms | **328 ms** | 368 ms |
| 光纤 + 中端手机 CPU | 253 ms | 276 ms | **1 716 ms** | 2 045 ms |
| 4G + 桌面 | 1 347 ms | 300 ms | **1 370 ms** | 1 425 ms |
| 4G + 中端手机 CPU（典型） | 1 705 ms | 1 164 ms | **1 962 ms** | 2 335 ms |

**结论：用户点开链接到看见列表，典型移动网络下约 2 秒。** 但"看见内容"远早于此——hero 区在 0.3～0.9 秒就已经画出来了（截图验证，不是白屏）。

### 2.2 这 2 秒花在哪

- **下载**：文档 607 KB（gzip），解压后 4.19 MB。4G 下 1.7 s，占 73%。
- **主线程**：优化前累计 Task 4.5 s（4× 降速），其中样式重排 ~2.3 s、脚本 ~0.15 s、其余为 HTML 解析与编译。
- **关键结构**：`PHONE_DATA` 内嵌在文档 **2.4%** 的位置，之后紧跟应用脚本（97.2%）。也就是说解析器在 10 万字节处就撞上一个 4MB 的同步脚本，必须全部下完、编译完才能继续——**这是首屏必须等整个文件的原因**。

## 三、瓶颈定位

### 3.1 真瓶颈（按影响排序）

**① Google Fonts：1.3 MB、54 个请求，比整个页面还大一倍**
实测同一页面：带字体总传输 **1 952 KB / 62 请求**，去掉字体 **608 KB / 8 请求**。字体 CSS 单项就 152 KB，之后还有数不清的 `woff2` 分片。它和 607 KB 的文档**抢同一条链路**，还把 load 事件拖到 4 s。目标是中文站点，`fonts.googleapis.com` 在境内本就经常连不上。

**② 数据体积：94.6% 的字节是"点开详情才需要"的内容**
4.19 MB 里：`specs` 占 56.3%、`fieldAudit` 占 25.1%，而**列表卡片只用到 14 个字段、合计 4.8%**。

| 方案（gzip 实测） | 体积 | 相对全量 |
|---|---:|---:|
| 全量 | 539 KB | 100% |
| 去掉 `fieldAudit` | 438 KB | 81% |
| 去掉 `specs`（保留搜索用纯文本 325 KB 另算） | 129 KB | 24% |
| 去掉两者 | 63 KB | 12% |

**③ 主线程布局：4× 降速下 ~2.3 s**
11～29 次布局、平均 97～225 ms/次。注意这是"少量大布局"，不是抖动（抖动会表现为成百上千次）。

### 3.2 已排除的伪瓶颈（测过，不采纳）

| 猜测 | 实测 | 判定 |
|---|---|---|
| 把 4MB 数据从 JS 字面量改成 `JSON.parse` 能省编译 | 首卡 2217→2174 ms（噪声内，连测 3 轮方向不稳） | **不采纳**，V8 对大数组字面量已经够快 |
| 卡片 `content-visibility:auto` 拖慢布局 | 去掉后 Layout 2 448→3 299 ms，首卡 1 984→2 217 ms | **反而更差**，保留 |
| 首屏骨架屏（40 个流光元素）拖慢首屏 | 去掉后 Layout 2 290、首卡 2 195 ms，无明显差异 | 保留 |
| 把数据脚本挪到文档末尾让首屏更早绘制 | 数据块后面紧跟应用脚本，**已经是最靠后的位置**，无处可挪 | 无操作空间 |
| 交互慢 | 打开详情 25 ms、打开对比页 27 ms、搜索 276 条 395 ms（含 200 ms 防抖） | **已经不慢**，不是本次瓶颈 |

## 四、已实施的优化

### ① 字体退出关键路径（`index.html` 头部）

原：`<link rel="preload" as="style">` + onload 切换 → 仍是文档子资源，抢占带宽并拖住 `load`。
现：改为 **`load` 事件之后用 JS 注入**（`media="print"` → onload 切 `all`，注入时不阻塞渲染）。设计不变，字体照样生效，只是晚一步换上去。

### ② 报价 API 健康探测延后到空闲

启动就 `initQuoteApi()`，后端不可达时要先直连 10 s 再走备用通道，期间占一条连接。改为 `requestIdleCallback`（6 s 兜底）。页面其余功能不受影响。

### 效果（4G + 中端手机 CPU，3 轮取中位数）

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 关键窗口总传输 | 1 952 KB / 62 请求 | 782 KB / 61 请求 | **−60%** |
| 看到列表 | 2 294 ms | 1 975 ms | **−14%（−319 ms）** |
| load 事件 | 4 057 ms | 2 318 ms | **−43%** |
| 主线程 Task 累计 | 4 491 ms | 2 413 ms | **−46%** |
| 回访（第二次打开） | 1 669 ms | 1 630 ms | 持平（符合预期：回访是解析受限，不含下载） |

三轮方向完全一致（首卡 2 289/2 333/2 294 → 1 995/1 975/1 944），不是单次噪声。

**为什么首卡只降 14% 而不是 60%**：下载与解析并行，字体只在两者重叠的那部分抢带宽。省下的 1.3 MB 主要改善的是"标签页转圈多久"（load）和移动流量，而不是"列表多久出现"。

## 五、改进方向与优先级

### P0（已完成，见上）
字体退出关键路径、健康探测延后。

### P1（收益最大，需要你决定）：拆分"列表数据"与"详情数据"

- 首屏只传列表字段（203 KB 原始，gzip 后约 60 KB）+ 应用代码，详情/审核数据（`specs` + `fieldAudit`）按需或空闲预取。
- 预期：冷启动下载 607 KB → **约 150 KB**，看到列表 2.0 s → **约 0.8 s**；回访的解析开销同样大幅下降。
- **代价与风险**：
  1. 单文件结构被打破（多一个数据文件），`file://` 直接打开会失效；
  2. **搜索依赖 `specs` 文本**（`specHay` 会检索全部规格值）——需要额外带一份搜索用纯文本（gzip 325 KB），否则搜「骁龙」「LTPO」这类只在规格里出现的词会漏；带了之后净收益从 −76% 缩到约 −20%；
  3. 详情首次打开需要一次请求（可用空闲预取掩盖）。
- **我的判断**：如果只拆 `fieldAudit`（不动搜索），能省 19% 且风险最小；若要拿到 −60% 以上，必须接受第 2 条的取舍，这属于产品决策。

### P2（低成本微调）
- 搜索防抖 200 ms → 150 ms：搜索耗时 −50 ms 左右，收益小，但改动也只有一行。
- 数据字段名缩写：gzip 已能压缩重复键名，实测收益 <3%，**不建议**。

### 不建议做的事
- 拆分后上 `Service Worker` 做离线：与"数据必须可追溯"的维护方式冲突，收益也不在前 2 秒。
- 虚拟滚动：分页已经解决了列表长度问题（见 `reports/paging_2026-10-31.md`），再叠加会与 `content-visibility` 打架。

## 六、怎么验证等待时间真的变短了

### 单次测量
```bash
python _jst/serve_gzip.py 8813 .            # 复现线上传输条件（别用 file://，没有网络耗时）
node _jst/load_bench.js http://127.0.0.1:8813/index.html 4g --cpu=4
```

### 判定标准（照这个判，不然容易被噪声骗）
1. **每个配置跑 3 轮取中位数**。同一版本多次测量：首卡波动 ±10%、FCP 可差 4 倍（252 ms ↔ 1 228 ms），单次对比没有意义。
2. **看这四个数**：`totalKB`（关键窗口传输）、`firstCard`（看到列表）、`load`、`taskMs`（主线程累计）。
3. **阈值**：`firstCard` 差异 <15% 视为无改善；`totalKB`/`load`/`taskMs` 这类带宽与主线程指标更稳定，>20% 才算数。
4. **必须同时看回归**：10 个 `_jst/check_*.js` 全绿（155 项断言），否则"变快"可能只是功能坏了。
5. **视觉确认**：`node _jst/shot_timeline.js <url> 400,900,1600,2400` 抓加载过程截图，确认没有白屏、字体最终确实生效。

### 本次验收记录
- 优化前后各 3 轮，方向一致（见第四节表格）。
- 回归：`smoke_func 15/15`、`check_paging 22`、`check_search 8`、`check_pinyin 12`、`check_efficiency 14`、`check_perf_fix 17`、`check_new_features 14`、`check_ux_p1 10`、`check_compare_features 9`、`check_detail_features 12` —— 全绿。
- 视觉：5 s 截图确认标题/正文/按钮排版与优化前一致。

## 七、线上实测：托管链路可能才是第一位的等待

本地测完再去打线上地址（`https://yishen510.github.io/phone-compare-site/`，4G + 4× CPU），结果完全不在一个量级：

| 指标 | 线上实测 |
|---|---:|
| 首字节 TTFB | 1 068 ms |
| **文档下载完成** | **32 206 ms** |
| 看到列表 | 33 039 ms |
| 回访（第二次打开） | 884 ms |

用 curl 裸拉一次交叉验证：`645 669 字节 / 37.2 秒 = 17 KB/s`。**这不是代码问题，是本机到 github.io 的链路吞吐只有 17 KB/s**（4 Mbps 的模拟限速根本不是瓶颈，实际连 0.14 Mbps 都不到）。645 KB 在这种链路上要 37 秒，前面所有的首屏优化都会被淹没。

必须说清楚的限制：这只是**我这台机器当前出口的实测**，不等于你的目标用户一定如此——GitHub Pages 在境内的可达性因地区/运营商差异很大。所以：

1. **请用真实手机、真实网络打开一次线上地址**，看列表多久出来（或用 Chrome 远程调试看 Network 面板里文档的耗时）。如果也是几十秒，那么优化重点就应该是托管，而不是代码。
2. 若确实慢，可选项（按落地成本排序）：
   - 换到国内可达性更好的静态托管（Cloudflare Pages / Vercel 等，无需备案，但国内速度仍不保证）；
   - 国内对象存储 + CDN（速度最好，但需要域名备案）；
   - 若短期不换托管：把 4 MB 数据拆成独立文件放到可达的 CDN 上，HTML 只留骨架——这时即使主站慢，列表数据也能从另一条链路取（与第五节 P1 是同一件事）。
3. gzip 已由 GitHub Pages 自动开启（645 KB vs 4.09 MB），这一层没有可挖的空间了。

## 八、已知边界

1. **测量环境是本机 Edge + 模拟限速**，不是真实 4G 网络；绝对数值会与线上有偏差，但用于前后对比是有效的。
2. **回访场景样本较小**（3 次），且本机磁盘/内存状态与真实手机不同；"回访 ~1.6 s 是解析受限"这个结论方向可靠，绝对数值仅供参考。
3. **字体延后到 load 之后**意味着慢网下字体替换发生得更晚（约 2.3 s 而非 1 s）。如果这在视觉上不能接受，替代方案就是彻底去掉远程字体（省 1.3 MB，中文用系统字体），但那会改变西文排版风格，需要你确认。
4. 报价 API 后端当前不可达，健康探测延后只是把它挪出首屏；**要不要保留这条探测本身**（转而只在用户点查价时连）是另一个待定项。
5. 第七节的线上吞吐（17 KB/s）是单机单次实测，样本很小；在得出"托管是瓶颈"的结论前，请在真实手机上复测。
