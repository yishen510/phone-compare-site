# 逐页展示（分页）——实现与实测报告

日期：2026-10-31
需求原文：*"如果页面出现卡顿，可以调整产品列表的展示方式：不再一次性列举所有产品，而是将展开方式的选择权交给用户，由用户自行决定是否逐页展开查看产品。请据此实现相应的交互逻辑，并在列表过长或渲染性能不足时默认采用该方案，确保页面流畅加载与响应。"*

---

## 一、设计取舍（先定参数，再写代码）

| 决策 | 取值 | 理由 |
|---|---|---|
| 每页条数 | **24** | 桌面 3 列 / 移动 1–2 列时，一页大致是 1.5–3 屏；再多就失去"先给一页"的意义 |
| 自动分页阈值 | **> 80 条** | 80 条以内一次性渲染的 Layout 成本在移动端 4× 降速下仍可接受；低于此值还弹「加载更多」属于打扰（搜出 5 条也要点一次） |
| 默认模式 | **auto** | 满足"列表过长时默认采用"；用户一旦手动选择就记住，不再被 auto 覆盖 |
| 用户选择的记忆 | `localStorage`：`phoneindex.pagemode.v1` | 与收藏 / 主题 / 密度同一套约定 |
| 重置时机 | 筛选、排序、视图切换 → 回第一页；收藏、对比 → **不重置** | 点个收藏就跳回第一页会把人甩出当前位置 |

**没有采用虚拟滚动**：它需要固定行高 + 滚动占位，与现有 `content-visibility:auto`（卡片本来就跳屏外渲染）+ 表格行复用机制会互相打架，且收益需要单独 A/B 才能判定。分页是这一需求下改动面最小、行为最可预期的方案。

## 二、交互行为

底部控制条（`#pagerBar`，无结果或结果 ≤24 条时自动隐藏）：

```
已显示 24 / 485 款      [ 加载更多 ]   全部展开
```

| 操作 | 行为 |
|---|---|
| **加载更多** | 追加一页（24 条）到列表末尾，**不重建**已加载的卡片（节点不替换、滚动位置不跳）；加载完最后一页后按钮自动隐藏 |
| **全部展开** | 一次性渲染全部结果（用户显式要求时才付这份成本） |
| **改为逐页加载** | 回到逐页模式；该按钮只在"已展开全部"时出现，两个模式可随时互切 |
| 刷新 / 下次访问 | 沿用上次的模式（`all` / `paged`）；从未选择过则走 auto |

补充的语义修正：

- 表格视图下「全选」只勾得到 DOM 里已渲染的行，因此表头复选框的 `aria-label` 会随状态变为 **「全选已显示的 24 款（共 485 款）」**，展开后变回「全选全部 485 款」——避免用户以为勾了全部却只导出 24 条。
- `#pagerInfo` 加了 `aria-live="polite"`：「已显示 48 / 485 款」变化时读屏会播报。
- 点击后排会隐藏的按钮（`全部展开` / `改为逐页加载`），把焦点移交给当前可见的那个按钮，键盘用户不会掉焦点。

## 三、实现（涉及文件）

**`index.html`**（唯一产品代码改动，+98 / −8 行）

| 位置 | 改动 |
|---|---|
| CSS `~L721` | `.pager-bar` 控制条样式（沿用 `--line` / `--muted` 变量，与全站一致） |
| HTML `~L1390` | `#pagerBar` 控制条，插在列表与空状态之间 |
| `state` | 新增 `pageMode:'auto'`、`visibleCount:0` |
| `~L1876` | `PAGE_SIZE=24`、`AUTO_PAGE_THRESHOLD=80`、`PAGE_MODE_KEY`、启动时读 localStorage |
| `gridSignature(arr, shownCount)` | **可见条数进签名**——见下方"踩坑 1" |
| `wantsPaged(total)` | 用户显式选择优先，否则按阈值 |
| `updatePager(total,shown,paged)` | 控制条文案 / 按钮显隐 / 表头全选标签 |
| `loadMore()` | 追加而非重建；表格走 `tbody.insertAdjacentHTML`，卡片走 `grid.insertAdjacentHTML` |
| `render()` | 计算 `fkey`（视图+排序+结果集首尾）决定是否重置 `visibleCount`；只把 `shown` 交给 `paintGrid` |
| 事件 `[data-pager]` | 三个动作 + 模式持久化 + 焦点接管 |

**未改动的关键路径**：`paintGrid` 的卡片分批（`PAINT_FIRST=12`）与表格一次性插入都保持原样，只是传入的数组从"全量"变成"当前已显示"。表格因此回到了"行数 === 结果数"的前提，`reorderTableRows` 的轻量行复用得以继续生效。

**`_jst/ux_bench.js`**（测量工具，+69 / −21 行）
- 支持传入目标文件（第二个参数），便于 A/B 对同一份代码的两个版本。
- 修正两处**测量缺陷**（不是产品 bug，但会让结论失真）：
  1. 步骤 2/3 原用 CDP 往返计时，同步完成的路径会被测成"轮询延迟"。改为**页面内 `performance.now()`**。
  2. 步骤 4/5 只等 `painting==='0'`，而防抖还没触发渲染时 `painting` 本来就是 `0`，会测到空转；且**切回卡片视图用的选择器 `[data-view="grid"]` 根本不存在**（实际是 `data-view="cards"`），导致这两步一直在表格视图下测量。已改正——**这两项数字与旧报告不可直接比较**。
- 新增「加载更多」「全部展开」两项测量。

**新增 `_jst/check_paging.js`**：22 项断言，覆盖默认逐页、追加语义（首卡片节点未被替换）、全部展开、改回逐页、少量结果不分页、排序回第一页、收藏不重置、表格分页、表头全选标签、模式持久化、无脚本报错。

**新增 `_jst/shot_pager.js`**：真实 Edge 截图核对控制条视觉（屏外卡片受 `content-visibility:auto` 跳过渲染，必须真滚动后截视口，否则拍到空壳卡片）。

## 五、性能实测（真实 Edge，390×844，CPU 4× 降速，各 3 轮取中位数）

A = 上一提交（一次性渲染全部）；B = 本次（逐页展示）。

复现方式（基线文件按需生成，不入库）：

```bash
git show HEAD:index.html > _jst/_baseline_index.html
node _jst/ux_bench.js _jst/_baseline_index.html   # A
node _jst/ux_bench.js index.html                  # B
```

| 指标 | A 基线 | B 分页 | 变化 |
|---|---:|---:|---:|
| 首屏首张卡片可见 | 2163 ms | 2082 ms | −4%（**噪声内，视为不变**） |
| 首屏到卡片画完 | 4562 ms | 3562 ms | **−22%** |
| 首屏累计 Layout | 2563 ms | 2283 ms | −11% |
| 首屏累计 RecalcStyle | 720 ms | 205 ms | **−72%** |
| 首屏累计 Script | 283 ms | 149 ms | **−47%** |
| 切换到表格视图 | 139 ms | 29 ms | **−79%** |
| 表格点击排序 | 783 ms | 95 ms | **−88%** |
| 搜索「骁龙」到画完（276 条） | 1129 ms | 395 ms | **−65%** |
| 清空搜索恢复全部 | 1284 ms | 285 ms | **−78%** |
| 点「加载更多」追加一页 | — | **10 ms** | 新增路径 |
| 点「全部展开」到画完 | — | **981 ms** | 显式请求时才付 |

**怎么读这张表（重要）**

- 首屏两项指标的噪声很大：同一版本连测 3 轮，`Layout` 波动 ±25%、`首张卡片` 曾出现 3115 ms 的单轮离群值（另两轮 2058 / 2082）。**小于 20% 的差异不足以判定**，所以「首屏首张卡片 −4%」不能当作收益。
- 可以判定为真实收益的是**倍数级差距**：RecalcStyle −72%、Script −47%、切表格 −79%、排序 −88%、搜索 −65%、清空 −78%。这些环节原来要把 485 张卡的 HTML 解析 + 样式重算 + 布局全做一遍，现在只做 24 张。
- **首屏首张卡片为什么没变**：首帧本来就只有 `PAINT_FIRST=12` 张卡，分页不影响它。首屏可感知的改善在"画完"这一步（4.56s → 3.56s）与"开始能顺畅交互"之前的时间。
- **成本没有消失，只是被推迟**：「全部展开」981 ms 就是这份账单。它远小于基线的"首屏到画完 4562 ms"，因为那 4.5s 里还含 4MB 单文件解析与脚本初始化（分页动不了这块，Layout 仍占首屏 50% 以上）。
- 表格视图的收益最大且最稳，因为原来 485 行的 `innerHTML` + 行复用判断是纯线性成本；现在每页 24 行，且 `reorderTableRows` 的"行数 === 结果数"前提重新成立。

## 六、已知边界

1. **首屏解析成本未变**：4.09 MB 单文件（内嵌 485 条数据）的下载 + 解析仍占首屏一半以上。要再降必须拆数据文件，属于另一个量级的改造。
2. **分页状态不进 URL**：`?brand=` 等筛选参数可分享，但"当前翻到第几页"不写入地址栏（模式选择在 localStorage）。若需要分享"第 3 页"，得再扩展 URL 协议。
3. **每页 24 条是固定值**，未随视口/设备能力调整。低端机与旗舰机同样 24 条——24 张卡在任何设备上都不构成瓶颈，因此没有再叠加设备探测（`hardwareConcurrency` / `deviceMemory` 在部分环境不可靠，容易变成新的不确定来源）。
4. **阈值 80 是经验值**：基于本机 4× 降速移动端模拟下"80 条一次性渲染仍在可接受范围"的判断，未做多机型实测。
